The **Review & Publish** page is the gateway for promoting policy changes to production. When a policy branch is submitted for review, it is locked for editing, and its lifecycle state changes to `IN_REVIEW`. Reviewers use this page to inspect changes, compose layers, run impact analyses, verify readiness, and publish the bundle.

## Review dashboard structure

The page stays unified as the policy promotion gateway, with three in-page stages:

### 1. Review changes

This stage combines the reviewer workflow with the compiled assembly steps:

* **Rules Diff** — Lists all rules added, modified, or removed between the parent baseline and the current branch revision.
* **Impact Analysis** — Cross-references changed rules against historical decision logs to predict the transaction-level impact (affected agents, connectors, and predicted deny rate changes).
* **Compose (Build) Step** — Integrates composition layer stacking. It merges the workspace branch rules with organization baselines and environment overlays, resolving conflicts using order-of-precedence rules (e.g., organization overrides workspace). Click **Compose** to build the final policy bundle and generate the unique `artifactHash`.
* **Approvals Panel** — Lists required approval seats based on the active workflow configuration. Reviewers can approve, request changes, or withdraw previous approvals.

### 2. Publish

This stage handles release readiness:

* **Publish Readiness** — Shows blocking reasons and the publish action for eligible publishers.
* **Compatibility Report** — Verifies that the composed bundle is fully compatible with the schemas of active agents.
* **AGT Verification** — Shows the latest verification result and stale or failing checks.
* **Export** — Provides the bundle artifact and AGT-compatible policy export.

### 3. History

This stage provides a chronological view of past branch revisions and rollback triggers.

## Publishing the bundle

Once all readiness checks are satisfied (all required approvals are complete, verification checks pass, and no blocking gateway escalations remain), the **Publish bundle** button in the header actions becomes active.

1. Open the **Publish** stage.
2. Click **Publish bundle**.
3. Confirm the action in the prompt.
4. The bundle is immediately registered as active. Connected agents will sync the new policy bundle automatically within their next heartbeat poll (default: 30 seconds).

## Reviewing and publishing from CI

The same two actions are available over the API, so a pipeline can gate a release on the reviewed path rather than bypassing it.

```bash
# 1. Is it publishable yet? (approvals:read)
curl -sS "https://app.spctre.dev/api/v1/policy/publishes/readiness?branchId=$BRANCH&revisionId=$REVISION" \
  -H "Authorization: Bearer $SPCTRE_REVIEWER_TOKEN"

# 2. Approve, in a role your principal holds (approvals:write)
curl -sS -X POST https://app.spctre.dev/api/v1/approvals \
  -H "Authorization: Bearer $SPCTRE_SECURITY_REVIEWER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"revisionId":"'"$REVISION"'","role":"Security","approvalStatus":"APPROVED"}'

# 3. Publish once readiness reports READY (publish:write)
curl -sS -X POST https://app.spctre.dev/api/v1/policy/publishes \
  -H "Authorization: Bearer $SPCTRE_PLATFORM_REVIEWER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"branchId":"'"$BRANCH"'","revisionId":"'"$REVISION"'"}'
```

**The key is the reviewer, not a way around them.** A service key acts as the principal it was issued to, and there is no actor field in either request body. So a key can only approve in the roles its owner holds, and can only publish what its owner could publish in the console. Because an approval is unique per revision and reviewer, a workflow requiring two roles still requires two keys held by two people — the same rule the Approvals panel applies.

<Callout type="warn">
  `approvals:write` and `publish:write` are **admin-issuable only** and are **never** granted to a runtime agent token from `spctre init`. A governed agent cannot approve or publish the policy that governs it.
</Callout>

### Reviewer identities

Two reviewers are needed for a workflow that requires two roles, and each needs their own key. `db/seeds/review-principals.ts` creates a Security reviewer and a Platform reviewer with a key each — only the second carrying `publish:write`, because publishing is a separate authority.

It lives beside the migrations because it needs the same credential they do: the tables it writes are row-level-scoped, so it runs on the owner connection. It therefore ships inside the migrate image and can be run as a task on the migrate job, inside the deployment's own network, rather than by opening a path to the database:

```bash
gcloud run jobs execute <prefix>-migrate --region <region> --wait \
  --args="node_modules/.bin/tsx,db/seeds/review-principals.ts" \
  --update-env-vars=SPCTRE_SEED_TENANT_ID=...,SPCTRE_SEED_WORKSPACE_ID=...
```

The overrides apply to that execution only; the job goes on running migrations. It prints the keys, so on a deployed environment they land in that execution's logs — re-running the seed reissues them, which is also the rotation path.

Every gate the console applies applies here, because it is the same publish path: required approvals, verification policy, rule validation, the evaluation request budget, managed-replay regressions, and unresolved gateway escalations. A revision that is not ready answers `422` with the reason rather than publishing. Publishing an already-published revision returns its existing `artifactHash`, so a retried pipeline step is safe.
